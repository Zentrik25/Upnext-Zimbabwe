# CLAUDE.md — NextJob Zimbabwe project rules
**Naming (D-33): the product is NextJob Zimbabwe (short: NextJob; https://nextjob.co.zw; tagline "Find what's next."). UPNEXT is the former name: it must not appear in public-facing branding, but internal identifiers (`UPNEXT_*` environment variables, cookie names, repository and Compose names, Django apps and tables, loggers) and historical records keep the old spelling. Resend is the selected e-mail provider (D-34); selection is not verification, B-01 stays open, nothing is configured or sent.**
**Current stage (updated 2026-10-28, M1): Phases 1 to 4 are technically accepted (Phase 4: commit ea54d91, CI 39065035043). Phase 5 (launch readiness and hardening, D-31/D-32) was accepted for engineering closure (baseline bba8168, D-35) and Phase 6A (employer portal, D-35) was formally ACCEPTED by the owner on 2026-10-18 (D-36). Phase 6B (seeker profile, rules-v1 For You, saved opportunities in a dashboard, e-mail alerts; authorised by D-38, ADR-0023) is implemented and MERGED into the integration branch `claude/new-session-t9v0fd` as PR #9 (merge commit `0cfae74`, 2026-10-18 23:29 UTC; the commit message records an owner-approved merge). No decision-register entry formally accepts Phase 6B, and its report (`docs/phase6b/PHASE6B_REPORT.md`) was written before the merge. Alerts are never sent while e-mail delivery is unverified (B-01); profile collection in production waits for reviewed privacy text (B-02). Backups are implemented and rehearsed in CI (encrypted, tamper-refusing, restore and re-application of deletions; `docs/engineering/BACKUP_AND_RESTORE.md`) but there is no off-server target, no measured restore on real infrastructure and no alert destination (B-07). No launch blocker is closed (`docs/governance/LAUNCH_BLOCKERS.md`) and nothing is deployed. Not authorised: AI matching, employer features beyond the Phase 6A scope (including native applications, CV upload, employer candidate search and payments), any deployment to the VPS (Phase 7 needs separate written approval), any change to The Granite Post or the existing Traefik/Nginx. Change of e-mail address is approved for the MVP only when it depends on verified e-mail delivery. Nothing is merged or deployed without separate owner approval.**

1. Read `00-READ-ME-FIRST.md`, `docs/governance/DECISION_REGISTER.md`, the applicable documents under `docs/product/`, `docs/design/`, `docs/engineering/` and `reference/approved-flat.html` before proposing work.
2. Treat confirmed decisions as binding. Never fill open questions with invented facts. Log questions and ask for approval.
3. Maintain a requirement-to-screen-to-API-to-test traceability table (`docs/governance/TRACEABILITY.md`) before implementation and keep it current.
4. No redesign of approved flat UI. No rounded cards or panels (buttons, inputs, selects and textareas use the 4px control radius, D-29), no shadows, gradients, glass effects or arbitrary palette changes. Tokens come from `docs/design/DESIGN_TOKENS.md`, extracted from the reference. Accessibility takes precedence over exact fidelity where the reference conflicts with WCAG 2.2 AA (D-19), but only through the minimum corrections listed in `docs/design/ACCESSIBILITY_DEVIATIONS.md`.
5. Architecture: Next.js + TypeScript frontend (`apps/web`); Django/DRF modular monolith (`apps/api`); PostgreSQL; Docker Compose; shared VPS Traefik -> Nginx. Redis/Celery are deferred (ADR-0004). Keep The Granite Post untouched.
6. Every document has status DRAFT until the user explicitly approves. Proposals are not approvals.
7. When asked for Phase 0, produce document gap analysis, contradictions, open decisions and proposed revisions only. Stop before code.
8. Build in small reviewable commits with tests, migrations, security review and per-phase approval gates. Never deploy without explicit permission. Never claim a check passed unless it was actually executed; record failures and limitations.
9. Editorial separation of duties (D-18, D-22) is a product invariant: nobody approves or verifies their own submission; publication needs another authorised person's approval of the exact revision (the author may then publish it); material changes invalidate approval; there is no Publisher role in the initial implementation (D-23); every transition is audited. Never write code or admin shortcuts that bypass the workflow, and enforce the rules transactionally on the backend.
10. Documents under `docs/archive/` are reference inputs only and do not override current documents.

## Repository layout (D-10)
`apps/web`, `apps/api`, `docs/`, `reference/`, `infrastructure/`, optional `packages/`. `reference/approved-flat.html` must never be edited.

## Source of truth
`docs/governance/DECISION_REGISTER.md` is authoritative (D-16). Where documents conflict, identify the conflict and request a decision; do not silently choose.
